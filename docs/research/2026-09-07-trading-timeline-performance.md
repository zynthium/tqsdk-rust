# TradingTimeline 高频回测性能验收

日期：2026-09-07。结论：当前不可变内存热路径成本低，未发现需要立即优化的瓶颈；
不能据微基准承诺任何策略中都“零影响”。本轮不修改生产实现或 public API。

## 环境和样本

AMD Ryzen 9 5900X，固定 logical CPU 2；Rust 1.98.0，release opt-level=3。
三轮测量，75 个生产 active Timeline（164,214 个交易区间），加合成规模测试。
每场景 100 批 × 20,000 次；下表是三轮的批平均中位数之中位数，包含循环和输入读取成本。
运行在共享机器上，CPU 频率和其他负载未被强制固定。

| 合法热路径 | 每调用耗时 | 等效单核吞吐 |
| --- | ---: | ---: |
| 单品种随机 duration | 31–42 ns | 约 2,400–3,200 万次/秒 |
| 单品种随机 forward/backward 900s | 64–84 ns | 约 1,200–1,600 万次/秒 |
| 按交易区间顺序 duration | 31–36 ns | 约 2,800–3,200 万次/秒 |
| 75 品种轮询 duration | 113 ns | 约 888 万次/秒 |
| 75 品种轮询 forward/backward 900s | 184 ns | 约 544 万次/秒 |

75 品种场景最差一轮的批平均 p95 分别约 121 ns、206 ns。
这是 **20,000 次调用的批平均分位数，不是单次调用 p95/p99**。
未做端到端策略吞吐对照，不把上述等效吞吐当成交易策略吞吐。

## 分配、磁盘、锁和内存

- 2.7 亿次计时 API 调用：零堆分配；计数中不含空循环基线和暖机。
- 独立 strace：600 万次热调用的 BEGIN/END 之间，无被跟踪文件/读取/futex 系统调用。
  加载前后的文件读取正常存在；源码热路径也仅使用不可变数组及二分查找，无 cache reader/mutex。
- 75 个 Timeline 合计保留约 16.80 MiB 堆请求字节，含决策与证据字符串；不是进程 RSS。
  其中交易区间数组及累计时间索引的有效元素大小合计约 5.01 MiB。
- 加载全部 75 个：三轮约 75、76、87 ms；单品种加载中位数约 1.05–1.14 ms。
  未清空 OS page cache，allocator 计数启用，因此不是冷磁盘延迟或最低加载成本。

## 随历史规模增长

随机 duration：256 段约 38 ns；4,096 段约 61 ns；65,536 段约 140 ns。
段数增至 256 倍，耗时约 3.7 倍，符合二分查找加 CPU cache 局部性的预期，未出现线性扫描退化。
这不表示不同 CPU cache 层级上的时间严格按数学对数增长。

## 高频回测的使用约束

1. 回测开始前 `load_active`，循环中复用同一不可变 Timeline。不要每 Tick 加载、反序列化、
   深拷贝 `TradingTimeline` 或扫描缓存。可让 worker 持有引用或事先共享的 Arc。
2. 回测前验证 `known_ranges`；零分配结论不适用于越界错误字符串构造。
3. 以较差局部性的 75 品种结果估算：每秒 100 万次 duration 约占 11% 单核时间，
   100 万次 shift 约占 18%。每 Tick 做一次 duration 加两次 shift，百万 Tick 约额外 0.48 秒 CPU。
   因而“每秒千万次重复查询”仍有真实预算压力，不能笼统承诺无影响。
4. 不因微基准预先增加 cursor、缓存层、锁或新索引；只有真实策略 profile 显示它占主要成本时再优化。

## 验证与重现

基准源码与逐场景统计未随仓库保留；本节仅保留性能结论。
release 三轮全部通过，计时热区零分配断言通过；独立基准 Clippy `-D warnings` 通过。
未进行跨线程扩展测试、冷缓存磁盘基准、单次调用尾延迟或策略端到端测试。
